Event identities always include channel + provider + ID. No module measures continuous performance or infers a component is defective.

## Architecture and rule review

`IDiagnosticModule` owns sources, matching conditions, grouping and incident construction. Existing five modules remain independently editable. `BroadModules` holds compact declarative rules for the added categories, with named fact codes, hypotheses, limits, severity, selected fields and actions. The collector derives candidate IDs from module sources; full matching remains in managed code. Avoid adding an ID without its provider/channel and a predetermined semantic fixture.

`InvestigationEngine` selects one applicable action from the incident's ordered recommendations, requiring the corresponding confirmed observation and respecting exclusions. Its deterministic rule table gives reasons and safety guidance. Entries influence only the same stable incident identity/category. Non-recurrence leads to observation, not “fixed”; incomplete/skipped steps establish no negative finding. Completed steps are not offered again unless their history is deleted. There is no learned model, percentage or automatic system modification.

Every accuracy fixture declares classifications, observation codes, permitted hypotheses, expected recommendations, evidence/context counts and prohibited conclusions. Original 36 fixtures are preserved; 20 new fixtures make **56**. Repeated and reversed input executions must match. Additional tests cover workflow exclusions, all outcomes, history restart/edit/delete/clear, corrupt/oversized input, redaction and HTML injection.

## Additional sources evaluated

- WER structured event metadata and Windows version are already used; they improve app-failure attribution and report context without a new inventory collector.
- Reliability Monitor is available through an explicit local button. Ingesting its history risks duplicating WER and adds compatibility work, so it remains a user comparison step.
- Crash dump metadata/content is not collected: permissions and private memory content require separate design. Relevant Stop records conditionally recommend trusted dump review.
- Driver/device inventory and Update history collectors are deferred. Current state does not prove historical state, and supported Windows UI checks provide the needed next step without broad collection.

## Evidence sources and validation limits

Added provider templates, channel mappings and numeric fields were checked against the installed Windows 11 build 26200 publisher metadata using read-only `Get-WinEvent -ListProvider`. This is Microsoft-shipped metadata, not message-text parsing in LogLens. DHCP events are on **Dhcp-Client/Admin**, not guessed to be System. NDIS ResetReason is displayed as a recorded value; unsupported reason-code translations are not invented.

Microsoft documents that [Kernel-PnP 219 may resolve through a later retry](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/event-id-219-when-device-plugged-in-windows-system). Existing CPER, Event 41 and storage sources are listed in [DIAGNOSTICS.md](DIAGNOSTICS.md).

Windows 10 manual compatibility, alternate provider versions/locales, real failure scenarios in every new category and accessibility/DPI testing are **not fully validated**. Unsupported schemas lose optional detail rather than triggering localized-string guesses. Planned detections are not advertised as implemented.
